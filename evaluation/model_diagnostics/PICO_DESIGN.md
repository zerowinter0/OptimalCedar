# PICO：cost model 与 DP 设计

本文说明 PICO 当前的代价模型与联合优化 DP 的设计思路，面向"读一遍就能明白
它在做什么、为什么这样做"的读者；具体标定细节见
`WIDTH_AND_FANOUT_20260915.md` 与 `PREDICTION_AUDIT_20260914.md`。

## 一句话定位

PICO 预测**整条 pipeline 端到端处理一条数据的耗时**，并在这个预测下用**一次
DP 同时决定**算子的执行顺序、融合、后端（本地 / SMP / Ray）与每个 stage 的并行
度、以及本地 worker 数 W。

## 一、cost model

### 1. 输入

一份 per-workload profile，包含三类测量结果：

| 内容 | 含义 |
|---|---|
| 算子单价 | 每个算子在本地 / SMP / Ray 上处理一条数据的耗时（trace 标定） |
| 宽度曲线 | 同一算子在 stage 内 1/2/4/8 个 actor 时的逐算子耗时与 stage 吞吐 |
| 边界与传输 | 跨 stage / 跨主机的每批提交成本、每字节带宽、预取窗口预算 |
| 干扰标定 | 同一计划在 W=2/4/8/16 下的实测/预测比值 |

### 2. 三层结构

**算子层**：算子 i 在宽度 1 下的单条耗时 `c_i`，来自 profile 的直接测量。

**stage 层**：一个 stage 是 DP 选出的算子子集 + 一种后端 + 一个宽度 a。

* 计算部分 = 子集内算子耗时之和，再除以**有效宽度**。
  有效宽度做了两件事：不会被外推到 profile 从未测量过的宽度之外（否则
  Plumber 的 `SMP(62)` 会被高估 4.6 倍）；并且按 `a^0.5` 而不是 `a` 折算
  ——实测一个 worker 下的第 2、4、7 个 actor 只能带来 470/762/1012 rec/s，
  远低于理想 797/1462/1903，因为一个 worker 只有一个提交循环在喂它们。
* 边界部分 = 跨 stage 的每批提交 + 每字节传输，单独计价，不摊进算子耗时。

**计划层**：把每个 stage 的成本累加到它所在的"通道"上，最终得分是各通道的
最大值：

* 本地算子与 Ray stage 的往返（序列化、跨主机 RTT、传输下限）记在同一条
  记录路径上，因为它们串行地发生在同一条数据上；
* SMP stage 若有多进程，则与本地链并行（取 max）；若只有单进程，它其实跑在
  worker 自己的槽位里，改为**直接加到记录路径**上——这正是"多一个 stage 反而
  变慢"的那类计划过去被看好的原因；
* 多个 Ray/SMP stage 的资源占用累加，受 64+64 CPU 预算约束。

最后乘上 worker 干扰因子（W 越大，同一台机器上的 worker 越互相挤压）与
GPU/互斥资源修正，得到"每个 worker 每条数据的毫秒数"。预测吞吐 =
`1000 × W / 该值`。

### 3. 与其它系统 cost model 的差别

| 系统 | 单位 | 是否区分后端 | 是否含宽度竞争 | 是否含边界/传输 |
|---|---|---|---|---|
| Cedar | 算子吞吐（加权） | 是 | 否（宽度=1） | 部分 |
| Plumber | 单条耗时 | 是（SMP 为主） | 是（理想线性） | 否 |
| Ray Data / 两阶段 | 单条耗时 | 是 | 理想线性 | 否 |
| **PICO** | **端到端每条数据耗时** | 是 | **实测曲线 + 实测 fan-out** | 是 |

核心差别是**标定对象**：其它系统标定"算子多快"，PICO 标定"这条 pipeline 多快"，
所以宽度竞争、通道串行、worker 干扰这些只在组合之后才出现的效果必须进模型。

## 二、DP 设计

### 状态与转移

* 状态 = （已放置的算子集合，缓存状态，已占用的 Ray/SMP CPU）；
* 转移 = 选择下一个 stage（算子子集 + 顺序 + 后端 + 宽度），代价由上面的
  计划层公式给出；
* 目标 = 最小化"每 worker 每条数据耗时"，同时受 CPU 预算约束；
* 支配剪枝：若一个 stage 用的资源不多于另一个、且四个通道分量都不更差，则被剪掉。

### 搜索空间

* 融合：任意连续子集可以合成一个 stage（同一后端一次执行），
  是否融合由 DP 的代价决定，不做启发式切分；
* 宽度：按阶梯枚举（1,2,3,4,6,8,12,16,24,32,48,64,…），因为服务时间在实测
  宽度之外已经不再变化，枚举中间每个整数只会浪费搜索预算；
* worker 数 W：对若干 W 各跑一次 DP，用"每 worker 耗时 × 干扰因子 / W"
  比较整体聚合吞吐，取最优；预算是**均分**给剩余候选的，保证在复杂负载上
  每个 W 至少能给出一个可行解。

### 复杂度控制

* 先构造三个贪心 incumbent（固定顺序、单并行块、全局块），用它们给出的上界
  剪枝；
* 复杂度预测器用依赖结构（合法前缀数、结构转移数、宽度组合）判断是否高复杂度；
* 任何一次搜索超时都会退回当前最优 incumbent，而不是让整个负载没有计划
  （旧版本在 dino / 文本负载上会直接超时且不产出计划）。

### 当前规模与耗时（2000 条小数据）

alpaca 8 算子约 130 s，clip 同量级，dino（18 算子）326 s，pile_pubmed/uspto
（19 算子）约 480 s；后两者的精确搜索会耗尽预算并返回 incumbent。

## 三、这套设计为什么必要（一句话版）

只有当模型能预测"这条 pipeline 多快"时，DP 才可能同时判断"该不该融合、该放
哪个后端、该给多少并行度、该开多少 worker"；把它拆成若干独立启发式（Cedar 的
分阶段优化、Plumber 的固定 SMP 宽度、两阶段的先排序再定价）时，每个局部最优
组合起来反而会输给一个统一的全局搜索——这正是我们在 clip / blip / 文本负载上
观察到的现象。
