# Multimodal Motivation Witness Design

## Objective

Produce a reproducible four-plan motivation experiment over the six-operator
multimodal pipeline shown in Figure 1:

- `U`: the unoptimized pipeline;
- `C`: the unmodified native Cedar optimizer output;
- `P`: the unmodified PICO optimizer output; and
- `M`: one representative alternative physical plan selected from a
  predeclared legal plan family.

The experiment must establish the following rankings:

1. Cedar cost: `P < C < M < U`;
2. PICO cost: `P < M < C < U`; and
3. held-out execution time: `P < M < C < U`.

The protocol must reject an unsuitable workload or candidate set rather than
alter an optimizer output, weaken a threshold after observing held-out data,
or introduce artificial operator delays.

## Pipeline and Semantics

The experiment uses the six operators already presented in the paper:

1. `N`: text normalization (CPU, text only);
2. `P`: perplexity filtering (CPU, text only);
3. `S`: safety filtering (its declared execution resource must match the
   device on which the model actually runs);
4. `A`: aesthetic filtering (GPU, image only);
5. `C`: CLIP filtering (GPU, image and text); and
6. `B`: BLIP filtering (GPU, image and text).

All candidate orders must preserve the declared semantic dependencies. Every
plan must return the same set of record identifiers. The temporary
`TrainingSampleBuilder` replacement is removed because it no longer matches
the workload presented in Figure 1 and enabled an invalid mixed-resource
fusion with CLIP.

Fusion is legal only when every member of a fused block declares the same
execution resource. A plan containing a mixed CPU/GPU fused block is rejected
before scoring or execution. The same rule applies inside Cedar and PICO plan
generation and in the materialized-plan validator.

## Resource Protocol

Profiling uses one local worker, one Ray actor per profiled Ray stage, one SMP
process per profiled SMP stage, and ten seconds per stage. Formal plans use
the existing shared resource allocator with `W=1`, `CPU_BUDGET=64`, and at
most one GPU in total.

The allocator, rather than the plan constructor, assigns all actor/process
counts. Plans may receive different widths when their stage structures differ,
but every width is derived from the same policy and total budget. Plan
construction cannot insert a special width to improve one candidate.

## Candidate Generation

`U`, `C`, and `P` have fixed provenance:

- `U` is materialized with every optimization disabled;
- `C` is generated by Cedar's native optimizer; and
- `P` is generated by `dp_optimizer.py` through the normal PICO selector.

Neither `C` nor `P` may be edited after generation.

The alternative-plan family is generated exhaustively from the following
predeclared dimensions:

- every semantically valid logical order;
- every partition of adjacent same-resource operators into legal fusion
  blocks; and
- local or Ray placement for each block when that variant was measured during
  profiling.

Caching remains disabled. SMP remains disabled for this motivation experiment.
Every candidate is passed through the shared resource allocator and rejected
if it is invalid, duplicates `U`, `C`, or `P`, exceeds the shared budget, uses
an unprofiled variant, or changes the output record set.

## Three-Stage Selection Protocol

### Stage 1: static preflight

Before any candidate execution, calculate Cedar and PICO costs for all legal
candidates. Retain only configurations for which:

- Cedar ranks `P < C`;
- at least one alternative has Cedar cost above `C`;
- PICO ranks `P < M < C` for at least one such alternative; and
- adjacent cost values differ by more than numerical tolerance.

Cost gaps and raw values are recorded for every candidate. A near-tie is never
rounded into a strict ordering. The report distinguishes a correct ordering
from a large estimation margin; the experiment does not impose an arbitrary
five-percent Cedar gap when the paper claim concerns ranking.

If no candidate passes, the run terminates as `no_static_witness` without
launching the long execution phase.

### Stage 2: calibration selection

Execute the statically valid shortlist on the fixed calibration split. Use
three round-robin repetitions after one warm-up epoch. A candidate is eligible
as `M` only when:

- `P < M < C < U` by median execution time;
- both adjacent optimized-plan gaps are at least 15%;
- bootstrap 95% confidence intervals for the optimized plans do not overlap;
  and
- every execution returns the same record identifiers.

If several candidates qualify, choose the candidate that maximizes the
minimum relative runtime gap to `P` and `C`; break remaining ties by the
canonical serialized-plan hash. This selection rule is fixed before observing
calibration measurements.

If no candidate qualifies, terminate as `no_calibration_witness`. Do not
change thresholds or candidate rules in the same run.

### Stage 3: held-out reporting

Freeze the selected configuration, four plan files, thresholds, profiles, and
SHA256 hashes. Execute the four frozen plans on the disjoint pilot/formal split
for three round-robin repetitions. Only this split supplies the runtimes shown
in Figure 1 or reported as validation data.

The held-out run succeeds only when it preserves output equivalence and the
declared runtime ordering. A failed held-out ordering is reported as a failed
hypothesis; it must not trigger automatic reselection.

## Data Separation and Reproducibility

The fixture manifest fixes calibration and held-out records before candidate
selection. Calibration measurements may select `M` and a threshold
configuration from a bounded, declared grid, but held-out records cannot
influence either decision.

Each output directory records:

- fixture and split hashes;
- model names and immutable revisions;
- threshold and profile hashes;
- optimizer identity and plan provenance;
- serialized plan and resource signature;
- all candidate costs, rejection reasons, and calibration measurements;
- the selected-plan rule and tie breaker; and
- per-repetition held-out runtimes and output record hashes.

The experiment must be restartable without silently mixing artifacts from
different code, profiles, thresholds, or fixtures.

## Validation

Unit tests cover semantic dependencies, same-resource fusion validation,
candidate enumeration, resource-budget enforcement, deterministic selection,
split isolation, cost-order checks, runtime-gap checks, confidence intervals,
and artifact hashing.

The implementation workflow is:

1. run the unit tests in the project container;
2. run a plan-only static preflight;
3. inspect the generated candidate audit artifact;
4. run the bounded calibration selection in the background; and
5. launch held-out execution only after the calibration gate succeeds.

No Figure 1 values are updated until the held-out result passes all checks.
